## 1. 背景・目的

### 1.1 背景

紙のノートを物理的に回す「交換日記」の体験を、離れた場所にいる相手とも共有できる Web アプリとして再構築する。デザインは Y2K カワイイ系の「Dreamy Pixel」スタイルを採用し、機能性だけでなく書く・読む体験そのものに情緒を持たせる。

### 1.2 目的

- ペアまたは小グループ（最大 6 人）で、順番にひとつのノートを回す体験をオンライン上で再現する
- 書き手のターン管理を仕組みで担保し、「誰の番か曖昧」「誰も書かなくなる」という従来の交換日記が抱える失速を防ぐ
- 装飾・演出を通じて「開く瞬間のワクワク感」を再現する

### 1.3 成功定義（MVP）

- 2 人のユーザーが招待リンク経由でノートに参加し、ターン制で書き合えること
- ターンが滞ったときに能動・受動の両方で催促できること
- ランディングページが Dreamy Pixel の世界観を伝えていること

## 3. 機能要件

### 3.1 認証

- **F-AUTH-01** メールアドレスの入力でマジックリンクを送信し、リンククリックでログインできる
- **F-AUTH-02** パスワード機能は持たない（運用負荷とフィッシング面の合理化）
- **F-AUTH-03** ログインセッションは DB セッション戦略で永続化する
- **F-AUTH-04** 同じメールアドレスのアカウントは 1 つに統合される

### 3.2 ノート（共有単位）

- **F-NB-01** ログインユーザーは新しいノートを作成できる（名前必須）
- **F-NB-02** 1 ノートのメンバー数は **2〜6 人**
- **F-NB-03** ノート作成者は自動的に最初のメンバー（順番=0）として登録される
- **F-NB-04** ユーザーは自分が参加するノート一覧を見られる（最終更新日時、次のターン者を含む）

### 3.3 招待

- **F-INV-01** ノートメンバーは招待 URL（コード付き）を発行できる
- **F-INV-02** 招待コードの有効期限は **発行から 7 日間**
- **F-INV-03** 招待コードは **1 回限り** で消費される
- **F-INV-04** 同じノートで複数の有効な招待コードを同時保持しない（既存があれば再利用）
- **F-INV-05** 招待 URL を未ログイン状態で開いた場合、サインイン後にそのまま招待受諾フローに戻る
- **F-INV-06** 既にメンバーであるユーザーが招待リンクを踏んだ場合、招待は消費されずにノート画面へ冪等遷移する
- **F-INV-07** メンバー数が上限に達しているノートの招待は受諾不可（適切なエラー画面を表示）
- **F-INV-08** 招待受諾は **同時実行に対して安全**（1 つの招待コードに同時に 2 人が受諾しても 1 人しか消費できない）

### 3.4 ターン制投稿

- **F-TURN-01** メンバーには順序（`orderIndex`）が割り振られ、書き込みは **次のターンの 1 名のみ** に許可される
- **F-TURN-02** 「次のターン」は、最新エントリ投稿者の次の `orderIndex` のメンバー
- **F-TURN-03** エントリが 1 件もない場合、最初のターンは `orderIndex = 0` のメンバー（=作成者）
- **F-TURN-04** ノートにはタイムライン形式でエントリ一覧が新しい順に表示される
- **F-TURN-05** 投稿者でないメンバーから投稿ページへの直接アクセスは拒否される（UI とサーバー両方で検証）

### 3.5 エディタ

- **F-EDIT-01** 投稿はプレーンテキスト + 改行のみ（Markdown 構文は解釈しない）
- **F-EDIT-02** 1 投稿の長さは **1〜5,000 文字**（空投稿不可）
- **F-EDIT-03** 投稿は作成のみ（編集・削除は MVP 対象外）

### 3.6 既読催促（ナッジ）

- **F-NUDGE-01** 自分のターンでないメンバーは、現在のターンのメンバーへ「もう書いた？」のナッジを送れる
- **F-NUDGE-02** 同じ送信者から同じ受信者へのナッジは **24 時間に 1 回まで**
- **F-NUDGE-03** ナッジ送信は記録される（`Nudge` レコード）
- **F-NUDGE-04** 最終投稿から `NUDGE_THRESHOLD_HOURS`（既定 72 時間）を超えたノートでは、現在のターンのメンバーにメール通知を送る（自動・1 日 1 回）

### 3.7 ランディングページ

- **F-LP-01** 未ログインユーザーが `/` にアクセスすると、Dreamy Pixel 世界観のランディングを表示する
- **F-LP-02** 構成セクション: ブートローダー / ヒーロー / マーキー A / 日記タイプライター / フォトカードスタック / マーキー B / KAWAII 散らし / メッセージ / アウトロ
- **F-LP-03** 主要 CTA は「あそびに いく」「にっき よむ」の 2 種で、いずれもサインインへ誘導する
- **F-LP-04** ログイン済みユーザーが `/` にアクセスするとノート一覧 (`/notebooks`) にリダイレクトされる

### 3.8 設定

- **F-SET-01** ユーザーは 4 種のカラーパレット（mint / strawberry / lavender / cream）から選択でき、選択は cookie で永続化される
- **F-SET-02** カスタムカーソル（ピンク矢印）を on/off できる

## 4. 非機能要件

### 4.1 パフォーマンス

- **NF-PERF-01** ランディングページは初回ペイント 2 秒以内（モバイル 4G 想定）
- **NF-PERF-02** ノート画面のエントリ取得は 200ms 以内（DB 上で `(notebookId, createdAt)` インデックスを活用）

### 4.2 セキュリティ

- **NF-SEC-01** 認証は Auth.js v5 の Resend Email Provider に従う。`AUTH_SECRET` は環境変数管理
- **NF-SEC-02** Cron エンドポイントは `Authorization: Bearer ${CRON_SECRET}` で保護
- **NF-SEC-03** すべてのミューテーションは Server Actions に集約し、入力は zod バリデーションを通す
- **NF-SEC-04** ノートへのアクセス権はメンバーシップでサーバー側検証する（IDOR 対策）
- **NF-SEC-05** 招待コードの推測困難性は nanoid(12) で確保（≒ 71 bit）

### 4.3 整合性・並行制御

- **NF-CON-01** 招待受諾は単一 Postgres トランザクション内で完結し、`updateMany` の WHERE 条件で atomic claim する（READ COMMITTED 下で安全）
- **NF-CON-02** ターン判定で参照する `Entry.findFirst` の orderBy には id をタイブレーカーに含める

### 4.4 アクセシビリティ

- **NF-A11Y-01** `prefers-reduced-motion: reduce` の環境では、ランディングセクションのアニメーションを停止する。ボタンのフォーカスリングや保存中スピナーなど、機能的フィードバックの transition は維持する
- **NF-A11Y-02** 装飾用 SVG には `aria-hidden="true"` を付与
- **NF-A11Y-03** カスタムカーソルは設定で無効化可能

### 4.5 デバイス・互換性

- **NF-DEV-01** モバイル・デスクトップ両対応（`clamp()` ベースの流体タイポ）
- **NF-DEV-02** モダンブラウザの最新 2〜3 バージョン（Chrome / Safari / Firefox）を対象

### 4.6 言語・コンテンツ

- **NF-LNG-01** UI 言語は日本語のみ。i18n フレームワークは導入しない

### 4.7 運用

- **NF-OPS-01** メール送信は Resend、SLA は同サービス基準
- **NF-OPS-02** 本番 DB は Neon、開発 DB は Docker Postgres 16
- **NF-OPS-03** デプロイは Vercel、Cron はその上で日次起動

## 5. ユースケース

### UC-01 新規ペアでの利用開始

1. ユーザー A が `/` を開く（未ログイン → ランディング）
2. CTA からサインインへ。メアド入力でマジックリンク受信
3. リンクをクリックしてログイン → ノート一覧（空）
4. 新規ノート作成（名前: 「テスト こうかんにっき」）
5. 招待 URL を発行してユーザー B に共有
6. B がリンクを開く → サインイン → 自動で招待受諾 → 同じノートへ参加
7. A が最初のエントリを投稿 → B のターンに切り替わる
8. B がエントリを投稿 → A のターンに切り替わる

### UC-02 ターン待ちのナッジ

1. A が投稿してから 24 時間以上経っているが、B が書いていない
2. A はノート画面で「もう書いた？」ボタンを押す
3. ナッジが記録される（24 時間以内に再送は不可）
4. 72 時間経過すると Cron が B にメール通知を送る

### UC-03 グループ拡張

1. 既存 2 人ノートのメンバーが招待 URL を発行
2. 新メンバー C が受諾 → メンバー末尾（orderIndex=2）として参加
3. 次のターンが C に回るのは、現在の最新投稿者の次のサイクル時

### UC-04 招待の同時受諾（並行制御）

1. A と D が同時に同じ招待リンクを踏む
2. 片方のトランザクションだけが `Invite.updateMany` で claim 成功
3. もう片方は `InviteUnavailableError` で適切な画面に遷移

## 6. データ要件

### 6.1 主要エンティティ

| エンティティ                          | 説明                                                                                             |
| ------------------------------------- | ------------------------------------------------------------------------------------------------ |
| User                                  | アカウント。Auth.js 標準フィールド + 表示名                                                      |
| Account / Session / VerificationToken | Auth.js 必須テーブル                                                                             |
| Notebook                              | 交換日記の単位                                                                                   |
| NotebookMember                        | ノートとユーザーの中間。`orderIndex` でターン順を保持。`(notebookId, orderIndex)` に unique 制約 |
| Entry                                 | 投稿。`(notebookId, createdAt)` にインデックス                                                   |
| Invite                                | 招待コード。`code` に unique、TTL は `expiresAt`、消費は `usedAt` で表現                         |
| Nudge                                 | 催促履歴。`(notebookId, toUserId, createdAt)` にインデックス                                     |

### 6.2 永続化方針

- DB: PostgreSQL 16
- ORM: Prisma
- マイグレーション管理: `prisma migrate`
- バックアップ: Neon の自動バックアップに依拠

## 7. 制約

- **C-01** 本番ホスティング先は Vercel + Neon を前提とする
- **C-02** メール送信は Resend を利用する（差し替えは将来検討）
- **C-03** デザインは「Dreamy Pixel」ハンドオフ（`/Users/yuki/Downloads/design_handoff_dreamy_pixel 2/`）を仕様の一次ソースとする
- **C-04** タイムゾーンは Asia/Tokyo（表示）、内部は UTC で保持
- **C-05** 1 ノートあたりのメンバー数は 2〜6 人（ハードリミット）
- **C-06** 1 投稿の文字数は 1〜5,000 文字
